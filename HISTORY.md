## 2026-11-09 — Интерактивный обзор: кликабельные показатели dashboard (блок 7)

Что сделано: задание §8 — "каждый показатель должен быть интерактивным и открывать соответствующую детализацию", "при переходе из показателя в список должны автоматически применяться соответствующие фильтры". `StatCard` (`DashboardPage.tsx`) теперь принимает опциональный `to` и оборачивается в `Link`. Кампании/Сотрудники/Группы ведут на соответствующие страницы. Отправлено/Открыто/Переходов/Отправлено форм/Скомпрометировано/Сообщили о фишинге ведут на `/reports?filter=<key>` — `ReportsPage.tsx` читает `filter` из query-параметра, применяет клиентский фильтр поверх уже загруженного `byEmployee()` (показывает только тех, у кого соответствующий счётчик >0), с индикатором активного фильтра и кнопкой сброса. Фильтрация клиентская, не серверная — осознанный компромисс ради простоты в рамках этой итерации, не масштабируется на очень большие объёмы сотрудников (fetch всех, фильтр на клиенте).

Основные файлы: `frontend/src/pages/DashboardPage.tsx`, `frontend/src/pages/ReportsPage.tsx`.

Результат: typecheck и build чистые. Задеплоено на стенд, проверено живым браузером: клик по карточке "Отправлено форм" → переход на `/reports?filter=submitted`, список сразу отфильтрован (видна только 1 запись с 2 отправками форм вместо полного списка), индикатор "Фильтр: Отправили форму" с кнопкой сброса работает, сброс возвращает к полному списку. ## 2026-11-09 — Multi-SMTP failover (блок 4, часть 2) — блок 4 завершён

Что сделано: архитектурное изменение из матрицы (§9) — если SMTP кампании не отвечает после всех `RETRY_LIMIT` (3) попыток pg-boss, перед окончательным отказом пробуются остальные активные SMTP-подключения по порядку (`SmtpConfigService.listIdsExcept`). Проверка только на последней retry-попытке (не на каждой промежуточной) — иначе было бы `RETRY_LIMIT × N_SMTP` реальных сетевых попыток вместо `RETRY_LIMIT + N_SMTP`. Отправка вынесена в общий метод `sendVia(smtpConfigId, target, campaign)` — используется и для основного SMTP, и для фолбэков, без дублирования логики персонализации/трекинга.

Основные файлы: `backend/src/modules/mailer/mailer-queue.service.ts`, `backend/src/modules/smtp/smtp-config.service.ts` (новый метод `listIdsExcept`), `backend/src/modules/mailer/mailer-queue.service.spec.ts`.

Результат: 3 новых unit-теста (успешный fallback, все SMTP исчерпаны, нет резервных подключений). Полный прогон backend — 87 тестов зелёных, typecheck и build чистые. Задеплоено на стенд, smoke-тест через живой браузер подтвердил, что приложение в целом стабильно после изменения (дашборд и логин работают).

**Блок 4 (почтовая инфраструктура) завершён целиком**: retry + персонализация (часть 1) + multi-SMTP failover (часть 2). Оба малых доделывания и единственное архитектурное изменение из матрицы по §4/§9 закрыты.

Известные проблемы: ни retry, ни failover не проверялись на живой реальной доставке письма — на стенде нет настоящего тестового SMTP-сервера (только unit-тесты с мокированным nodemailer-транспортом). Если понадобится живая проверка — нужен mailpit/MailHog-контейнер на стенде, сейчас его нет.

## 2026-11-09 — Граббер: локальное сохранение ресурсов (блок 3, часть 2) + цепочка живых фиксов

Что сделано: граббер страниц больше не зависит от доступности исходного сайта после сохранения — ключевое требование §3 задания, ранее нарушавшееся (`<base href>` на исходный домен). `screenshot-service` перехватывает сетевые ответы (CSS/JS/изображения/шрифты) во время headless-рендера через `page.on('response')`, backend сохраняет их на диск (сначала во временную папку по `cloneId`, переносится под постоянный `pageId` при реальном сохранении страницы) и раздаёт через `GET /lp/:slug/assets/:filename`.

Код был написан, типы и 79 unit-тестов прошли, сборка чистая — но реальная проверка живым клонированием en.wikipedia.org (не синтетическая тестовая страница) на стенде нашла **4 последовательных реальных бага**, которые ни один unit-тест и ни одна компиляция не поймали:

1. **413 на сохранении**: `htmlSource` реального сайта легко превышает дефолт Express (100kb). Первая попытка фикса (`app.use(express.json({limit}))`) не сработала — NestJS регистрирует свой body-parser раньше любого вручную добавленного `app.use()`. Правильный фикс — `app.useBodyParser('json', {limit})`, официальный документированный способ (нашёл через WebSearch, не из памяти).
2. Тот же 413 **после** фикса №1 — потому что настоящая причина была не в NestJS, а в nginx-прокси фронтенда (`frontend/nginx.conf`, дефолт `client_max_body_size` 1 МБ), который отклонял запрос раньше, чем он доходил до backend.
3. **Предпросмотр в редакторе не показывал локальные ресурсы** до сохранения страницы — `srcDoc` резолвит относительные пути относительно родительской страницы `/pages/...`, не относительно виртуального origin лендинга. Решение — отдельный `@Public()` preview-эндпоинт по `cloneId` (защита — непредсказуемость UUID, тот же принцип что у `trackingToken`) и вставка `<base href>` на фронтенде.
4. Тот же баг **на финальной сохранённой странице** — `/lp/assets/...` вместо `/lp/{slug}/assets/...` (404), по той же причине резолва относительных путей. Симметричный фикс — вставка `<base href="/lp/{slug}/">` при раздаче на `public-pages.controller.ts`, только для страниц с `sourceUrl` (граббер).

Основные файлы: `backend/src/main.ts`, `backend/src/modules/pages/public-pages.controller.ts`, `frontend/nginx.conf`, `frontend/src/pages/PageEditorPage.tsx`, `screenshot-service/server.js`, `backend/src/modules/pages/screenshot.service.ts`, `backend/src/modules/pages/pages.controller.ts`, `backend/src/modules/pages/asset-content-type.ts` (новый).

Результат: полный живой прогон успешен — клонирование en.wikipedia.org/wiki/Phishing, предпросмотр со стилями в редакторе, сохранение (201, не 413), финальная публичная страница `/lp/test-local-assets-2` отдаёт полностью стилизованную копию (скриншот подтверждён: логотип, навигация, типографика, картинки — все с `192.168.1.107`, не с `en.wikipedia.org`). Тестовая страница оставлена на стенде как живое демо.

Известные проблемы: сохраняются только ресурсы, перехваченные за время `networkidle`-рендера — динамически подгружаемые модули (MediaWiki `load.php`) и ленивые thumbnail'ы по-прежнему идут на исходный сайт (ожидаемое, задокументированное ограничение headless-снимка). Временные папки несохранённых клонов не чистятся автоматически.

**Вывод для процесса**: все 4 бага прошли мимо compile+test+build и были бы невидимы без реального клонирования настоящего сложного сайта на живом стенде — синтетические/тривиальные тестовые страницы (`example.com`, ручной HTML) не создают условий, в которых эти баги проявляются (маленький HTML не превышает лимиты, страница без внешних ресурсов не задействует asset-пути вообще).

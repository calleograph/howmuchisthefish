# Системные требования

Цифры ниже основаны на составе сервисов (PostgreSQL + Node.js backend +
nginx-статика + опционально Caddy) и доступных измерениях на этапе
разработки — **не на нагрузочном тестировании под реальной производственной
нагрузкой**, которое ещё предстоит провести перед первым релизом. Это явно
отмечено как не проверенное — не планируйте мощность по этим цифрам как по
гарантии.

## Минимальная конфигурация (для оценки/небольшой организации, < 100 сотрудников)

| Параметр | Значение |
|---|---|
| CPU | 2 ядра |
| RAM | 2 ГБ |
| Диск | 10 ГБ свободно (плюс место под резервные копии) |

## Рекомендуемая конфигурация (до нескольких тысяч сотрудников)

| Параметр | Значение |
|---|---|
| CPU | 4 ядра |
| RAM | 4 ГБ |
| Диск | 20+ ГБ (зависит от объёма загружаемых материалов и резервных копий) |

## Поддерживаемые ОС

- Ubuntu 22.04 LTS, 24.04 LTS
- Debian 12 (bookworm), 13 (trixie)

## Docker

- Docker Engine 24+
- Docker Compose plugin (`docker compose`, не отдельный `docker-compose`)

Установщик (`scripts/install.sh`) ставит оба автоматически на
поддерживаемых ОС, если их ещё нет.

## Время первой сборки на медленных/виртуализированных дисках

Первая сборка Docker-образов (`install.sh`, этап `build`) включает `npm ci`
для ~1000 пакетов backend и финальный `chown -R` над всем деревом
`node_modules` в runtime-слое образа. На быстром SSD это занимает секунды.
На медленном или сильно нагруженном виртуальном диске (замечено на тестовом
стенде на KVM/QEMU: загрузка диска 80–99% по `iostat`, журналируемая
ФС ext4) этот `chown` может растянуться на час и более — каждый файл,
унаследованный из нижнего read-only слоя образа, Docker сначала копирует в
верхний слой (overlay2 "copy-up") с синхронным commit в журнал ФС, и при
десятках тысяч мелких файлов в `node_modules` эта операция становится
узким местом. Это не зависание и не баг — `docker compose build` в это время
жив и прогрессирует (проверяется через `ps aux` или `cat /proc/<pid>/io`,
счётчик `write_bytes` должен расти). Разовая стоимость: повторные
`docker compose build` переиспользуют закэшированные слои и не повторяют
этот шаг, пока зависимости (`package*.json`) не меняются.

Если диск виртуальной машины физически больше, чем видит `df -h /`, причина
часто в LVM: установщик Ubuntu Server иногда создаёт корневой логический том
меньше всего объёма диска, оставляя разницу невыделенной в volume group.
`scripts/preflight.sh` (запускается автоматически на этапе `prerequisites`)
обнаруживает это и печатает команды для онлайн-расширения тома
(`lvextend` + `resize2fs`), ничего не меняя самостоятельно.

## Сетевые требования

| Назначение | Требование |
|---|---|
| Входящий HTTPS (встроенный вариант) | Порты 80 и 443 доступны извне, DNS A-запись на сервер |
| Входящий HTTPS (за внешним proxy) | Порт, который слушает ваш proxy; backend/frontend остаются на loopback |
| Исходящий SMTP | Доступ к вашему SMTP-релею (обычно порт 587 или 465) |
| Исходящий HTTPS | Для автоматического получения сертификата Let's Encrypt (встроенный вариант) |

## DNS и TLS

Для встроенного HTTPS: A-запись домена на IP сервера, порты 80/443 открыты —
Caddy сам получает и обновляет сертификат Let's Encrypt, ручная настройка не
требуется.

Для варианта с внешним reverse proxy: TLS-сертификат — забота вашего proxy
(это может быть тот же Let's Encrypt, корпоративный CA или self-signed для
внутренней сети).

## Исходящий SMTP

Платформа не поднимает собственный почтовый сервер по умолчанию (задание:
упрощение установки и сопровождения) — нужен исходящий SMTP-релей:
корпоративный Exchange/Office 365, SendGrid, Mailgun или аналогичный. См.
[SMTP_SETUP.md](SMTP_SETUP.md).

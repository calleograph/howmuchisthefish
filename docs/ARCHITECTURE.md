# Архитектура

## Принцип

Модульный монолит, не микросервисы. Решение принято для продукта,
устанавливаемого одной организацией на свой сервер: независимое
масштабирование сервисов не нужно, а операционная сложность микросервисов
(отдельный message broker, межсервисные контракты, распределённая
трассировка) — не нужна тоже. Границы модулей внутри backend повторяют
функциональные области (пользователи, кампании, рассылка, отчёты) так, что
выделение в отдельный сервис остаётся возможным позже, если потребуется.

## Компоненты

## Backend-модули

| Модуль | Отвечает за |
|---|---|
| `auth` | Локальный вход (JWT), OIDC, SAML, защита от перебора |
| `employees` | CRUD сотрудников, CSV-импорт с построчной валидацией |
| `groups` | Группы сотрудников |
| `templates` | Почтовые шаблоны (MJML→HTML), переменные персонализации |
| `pages` | Учебные страницы, публичная раздача по `/lp/{slug}` |
| `events` | Регистрация событий (открытие/клик/отправка формы), публичные роуты `/t/*` |
| `smtp` | SMTP-подключения, шифрование паролей, тестовая отправка |
| `mailer` | Очередь отправки писем (pg-boss), персонализация, трекинг |
| `campaigns` | Конечный автомат состояний кампании, выбор получателей |
| `reports` | Агрегаты, срезы, CSV-экспорт |
| `crypto` | Шифрование секретов (AES-256-GCM, ключ `APP_MASTER_KEY`) |

## Почему без Redis/NATS

Очереди (отправка писем, отложенный запуск кампаний) реализованы через
[pg-boss](https://github.com/timgit/pg-boss) — очередь поверх PostgreSQL,
который и так есть в стеке. Это не ещё один дополнительный компонент для
установки и сопровождения. Межсервисная шина (NATS) не нужна в монолите —
все модули общаются вызовами в рамках одного процесса.

## Маршрутизация

Backend слушает два вида путей:

- **`/api/*`** — авторизованный REST API администратора (все модули выше).
  Отделён префиксом от путей фронтенда (`/employees`, `/campaigns` и т.п. —
  это маршруты React Router, не REST-эндпоинты).
- **`/health`, `/lp/*`, `/t/*`** — публичные пути без префикса: `/health`
  для Docker healthcheck, `/lp/{slug}` — учебные страницы (короткая ссылка
  в письме), `/t/pixel.gif` и `/t/event` — трекинг открытия/клика/отправки
  формы (тоже короткие ссылки, встраиваются в письма и HTML страниц).

Caddy/внешний reverse proxy должен направлять эти пути на backend, всё
остальное — на статику frontend (см. `deployment/Caddyfile` как референс).

## Модель данных кампании

```
Campaign (конечный автомат: DRAFT→SCHEDULED/RUNNING→PAUSED/FINISHED/FAILED)
  ├── template: MailTemplate (MJML-исходник + скомпилированный HTML)
  ├── page: LandingPage (HTML учебной страницы)
  ├── smtpConfig: SmtpConfig (зашифрованный пароль)
  └── targets: CampaignTarget[] (один на сотрудника, с trackingToken)
        └── events: CampaignEvent[] (EMAIL_SENT/OPENED/LINK_CLICKED/FORM_SUBMITTED)
```

`CampaignEvent` **намеренно не имеет поля для значений формы** — это
архитектурное решение, не просто правило валидации; см.
[SECURITY.md](SECURITY.md#механизм-безопасной-формы) для деталей механизма.

## Обновление (root-helper)

Backend-контейнер работает от непривилегированного пользователя (uid
10001) и не имеет доступа к Docker socket хоста. Обновление и резервное
копирование из веб-интерфейса выполняет отдельная systemd-служба на хосте
(root-helper, `scripts/root-helper/`), которой backend передаёт запросы
через файловый каталог обмена с ограниченными правами — не напрямую.
Подробности — [UPDATE.md](UPDATE.md).

## Развёртывание

Docker Compose, не Kubernetes — решение для целевой аудитории (одна
организация, свой сервер, не выделенная DevOps-команда). Два пути
публикации (встроенный HTTPS через Caddy или за внешним reverse proxy) —
через override-файлы `compose.caddy.yml`/`compose.external-proxy.yml` над
общим `compose.yml`, не дублирование сервисов.

# Модель безопасности

## Назначение продукта

Платформа предназначена исключительно для авторизованного обучения
сотрудников собственной организации методам противодействия фишингу.
Использование против людей без их ведома, вне рамок согласованной
программы повышения осведомлённости, может быть незаконным — ответственность
за корректное использование лежит на организации, развернувшей платформу.

## Механизм безопасной формы (по умолчанию)

По умолчанию для КАЖДОЙ учебной страницы действует требование, зафиксированное
в исходном техническом задании продукта: **значения, введённые сотрудником в
форму учебной страницы, не достигают backend** — ни в теле запроса, ни в
логах, ни в диагностике, ни в резервной копии.

Это не просто правило бизнес-логики ("не сохранять поле X"), а свойство
самого механизма отправки, реализованное на двух независимых уровнях:

1. **Клиентский скрипт** (`backend/src/modules/pages/safe-form-injector.ts`,
   функция `buildSafeFormScript`), встраиваемый на учебную страницу по
   умолчанию, физически не читает значения полей формы — не обращается к
   `FormData(form)`, не читает `.value` элементов. При отправке формы он
   отправляет на сервер только `{token, type: "form_submitted"}` — факт
   события, независимый от того, что ввёл сотрудник.

2. **Серверная валидация** (`TrackEventDto` с `ValidationPipe({whitelist:
   true, forbidNonWhitelisted: true})`) отклоняет весь запрос целиком (HTTP
   400), если в теле `/t/event` присутствует хоть одно поле сверх ожидаемых
   `token` и `type`. Даже если бы клиентский скрипт был обойдён или
   подменён, этот путь не примет полезную нагрузку с дополнительными полями.

Схема базы данных (`CampaignEvent` в `prisma/schema.prisma`) не имеет
столбца для значений формы — архитектурно невозможно случайно его туда
записать через этот путь.

## История решения о значениях форм (пересмотрено в v0.3.0)

Изначальная версия продукта (до v0.3.0) делала описанное выше гарантией БЕЗ
исключений — захват значений формы не предусматривался архитектурой вообще.
Это решение было сознательным и явно противопоставлялось распространённой
в индустрии практикой некоторых похожих платформ хранить и показывать
введённые значения (включая пароли) открытым текстом без какой-либо защиты.

В v0.3.0 владелец продукта явно запросил возможность установить факт
**реальной** компрометации (не только факт отправки формы) — для отчётности
руководству: действительно ли сотрудник ввёл рабочий пароль, или просто
нажал кнопку из любопытства. Это осознанное архитектурное решение, принятое
с пониманием компромисса:

- **Захват выключен по умолчанию для каждой учебной страницы**
  (`LandingPage.capturesCredentials = false`). Администратор включает его
  явно для конкретной страницы — это не глобальная настройка системы.
- Когда захват включён, используется ОТДЕЛЬНЫЙ клиентский скрипт
  (`buildCapturingFormScript` в том же файле) и ОТДЕЛЬНЫЙ серверный путь
  (`POST /t/credential`, не `/t/event`) — обычные страницы продолжают
  использовать прежний безопасный путь без каких-либо изменений в
  поведении.
- Захваченные значения шифруются немедленно при приёме AES-256-GCM
  **отдельным** ключом (`CREDENTIAL_ENCRYPTION_KEY`), который НЕ является
  производным от `APP_MASTER_KEY` и не хранится в том же `.env`, что
  остальная конфигурация приложения (`backend/src/modules/crypto/crypto.service.ts`).
- Чтение расшифрованного значения возможно только через явный эндпоинт
  (`GET /campaigns/:id/events/:eventId/credential`), доступный исключительно
  роли ADMIN, и каждый вызов — успешный или нет — записывается в
  `AuditLog` (`action: reveal_captured_credential`, с `userId`, `ipAddress`,
  временем).
- Повторный ввод одного и того же значения за одну отправку формы не
  создаёт дубликатов — дедупликация по SHA-256 хешу значения
  (`CapturedCredential.valueHash`), так что отчёт показывает реальное
  количество РАЗНЫХ введённых вариантов, не количество кликов.
- Метрика "скомпрометировано" на дашборде считает УНИКАЛЬНЫХ сотрудников
  (по `CampaignTarget`, не по количеству событий) — тот, кто подобрал
  несколько паролей подряд, учитывается как один человек, не как несколько
  инцидентов.

**Честная граница этой защиты**: это НЕ полноценная клиентская E2E-схема, где
сервер физически не может расшифровать данные ни при каких условиях. При
полной компрометации сервера целиком (не только дампа БД/бэкапа БД, а
доступа к работающему окружению приложения) оба ключа —
`CREDENTIAL_ENCRYPTION_KEY` и `APP_MASTER_KEY` — технически достижимы.
Отдельный ключ защищает от более вероятного сценария — утечки через дамп
базы данных или резервную копию БД без доступа к серверу целиком — но не
является абсолютной гарантией. Администратор, которому требуется более
строгая защита (ключ, физически недостижимый даже при полной компрометации
сервера), должен реализовать клиентскую E2E-схему самостоятельно — это
отдельная, более сложная задача, не включённая в эту версию.

## Граббер страниц (клонирование форм для учебных страниц)

Начиная с v0.3.0 поддерживается клонирование произвольного URL в HTML
учебной страницы — ранее эта функция была намеренно исключена (см.
исторический пункт ниже), решение пересмотрено по явному запросу владельца
продукта.

- Реализовано как опциональный эндпоинт `/clone` в уже существующем
  `screenshot-service` (отдельный Docker-образ с Chromium, не в основном
  backend-образе) — headless-рендер страницы, не простое скачивание HTML:
  работает и для SPA/JS-рендерящихся форм (современные корпоративные
  SSO-страницы), не только для статичного HTML.
- Результат клонирования НЕ сохраняется автоматически — администратор видит
  HTML в редакторе (`POST /pages/clone-preview`) и явно решает, сохранять
  ли страницу, прежде чем она станет реальным лендингом кампании.
- `action`/`method` у всех `<form>` в склонированном HTML убираются
  (`backend/src/modules/pages/form-rewriter.ts`) — дополнительный барьер
  поверх перехвата submit на JS-уровне: если по какой-то причине наш
  скрипт не выполнился (блокировщик скриптов, сетевая ошибка), форма со
  своим исходным `action` не должна отправить данные сотрудника на реальный
  внешний сайт.
- **Известные ограничения**: ресурсы страницы (CSS/JS/изображения)
  продолжают подгружаться с исходного домена через `<base href>` — страница
  перестанет корректно отображаться, если оригинальный сайт станет
  недоступен или изменит структуру; страницы с анти-клонированием или
  CSP-защитой, блокирующей встраивание, могут клонироваться некорректно;
  аутентификационные экраны, требующие предварительный вход (не просто
  форму логина), клонировать невозможно в принципе.
- **Ответственность**: клонирование чужого визуального дизайна формы входа
  для учебных целей внутри собственной организации — распространённая
  практика security-awareness индустрии (используется GoPhish, King
  Phisher и аналогами), но использование полученного результата остаётся
  на ответственности организации, применяющей платформу — см. раздел
  "Назначение продукта" выше.

## Анти-энумерация трекинг-токенов

Эндпоинты `/t/event` и `/t/pixel.gif` не раскрывают внешнему наблюдателю,
существует ли переданный `token` — ответ одинаков для валидного и
невалидного токена. Это не даёт перебором токенов определить, кто из
сотрудников является целью кампании.

## Классификация автоматических событий

Корпоративные почтовые шлюзы и антифишинговые сканеры (Proofpoint,
Mimecast, Microsoft Safe Links и т.п.) могут автоматически открывать
письма и переходить по ссылкам до того, как это сделает реальный
сотрудник. Такие события помечаются флагом `isSuspiciousAutomated` по
эвристике User-Agent (`backend/src/modules/events/bot-detection.ts`) —
**это эвристика, не гарантия**: отчётность должна учитывать её
ограниченность, а не считать флаг абсолютно точным.

## Аутентификация и авторизация

- Локальные пароли — bcrypt (12 раундов), JWT для сессий
- Защита от перебора: блокировка на 5 минут после 5 неудачных попыток входа
  с одного email (in-memory — не переживает перезапуск процесса в текущей
  версии, см. [FEATURE_MATRIX.md](FEATURE_MATRIX.md))
- Ролевая модель: ADMIN / EDITOR / VIEWER, проверяется на уровне каждого
  эндпоинта
- SMTP-доступ — только роль ADMIN (контроль над инфраструктурой доставки)
- OIDC и SAML — альтернативные способы входа через корпоративный каталог
  (SAML как legacy-путь; при использовании библиотеки `node-saml` убедитесь,
  что версия ≥5.1.0 — более ранние версии уязвимы к CVE-2025-54419,
  authentication bypass через подмену assertion)

## Секреты

- Пароли SMTP-подключений и другие секреты конфигурации, сохранённые через
  интерфейс, шифруются AES-256-GCM ключом `APP_MASTER_KEY` — в открытом
  виде не возвращаются ни через API (`hasPassword: true/false` вместо
  значения), ни в резервных копиях
- Захваченные значения учебных форм (если администратор явно включил
  `capturesCredentials` для страницы) шифруются ОТДЕЛЬНЫМ ключом
  `CREDENTIAL_ENCRYPTION_KEY` — см. "История решения о значениях форм" выше
- Секреты развёртывания (`DB_PASSWORD`, `JWT_SECRET`, `APP_MASTER_KEY`,
  опционально `CREDENTIAL_ENCRYPTION_KEY`) генерируются установщиком
  случайно, не захардкожены
- Логи исключают `Authorization`-заголовок, поле `password` и поле `fields`
  (значения учебных форм) из тела запроса (redact-правила в конфигурации
  логгера, `backend/src/app.module.ts`)

## Защита API

- `ValidationPipe({whitelist: true, forbidNonWhitelisted: true})` глобально
  — любые поля сверх ожидаемых в DTO отклоняют запрос целиком
- Rate limiting на уровне приложения (настраивается через
  `RATE_LIMIT_TTL_SECONDS`/`RATE_LIMIT_MAX`)
- `helmet()` — стандартные защитные HTTP-заголовки
- Публичная страница `/lp/{slug}` отдаётся со строгим
  `Content-Security-Policy` и `X-Frame-Options: DENY`

## Известные ограничения текущей версии

См. [FEATURE_MATRIX.md](FEATURE_MATRIX.md) — список функциональности,
которая объявлена, но не реализована или не проверена на момент выпуска
0.1.0. В частности: самоподписанные SMTP-сертификаты не поддерживаются
(`rejectUnauthorized: true` без исключений), ограничение частоты входа не
переживает перезапуск backend.

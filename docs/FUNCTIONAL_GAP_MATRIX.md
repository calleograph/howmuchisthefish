# Матрица функциональной полноты (аудит 2026-11-09)

Сопоставление текущей реализации HowMuchIsTheFish с функциональной картой донора StopPhish, GoPhish и Microsoft Attack Simulation Training. Чистый аудит — основа для планирования дальнейшей разработки (см. PROJECT.md → «Текущие незавершённые задачи»).

Легенда объёма: **малое доделывание** — инфраструктура есть, нужно прокинуть/добавить поле; **новый модуль** — отдельная сущность/сервис с нуля; **архитектурное изменение** — затрагивает деплой/маршрутизацию/несколько модулей сразу.

## 1. Управление доменами

**Статус: отсутствует.** В схеме есть только `Campaign.allowedDomainsOverride` — allow-list email-доменов сотрудников при наборе целей, это не управление доменами публикации. Нет модели `Domain`, DNS-проверки, привязки к SMTP/странице, верификации владения.
Объём: **новый модуль**, с нуля.

## 2. Привязка доменов к сайтам/учебным страницам

**Статус: отсутствует.** `LandingPage.slug` живёт на едином `PUBLIC_BASE_URL`, нет понятия "эта страница на домене X".
Объём: **архитектурное изменение** (маршрутизация по Host-заголовку + модуль Domains как предпосылка).

## 3. Почтовые шаблоны

**Статус: готово (база), персонализация частичная.** `templates/mjml-render.service.ts` — полный CRUD, MJML→HTML, `extractVariables` по `{{var}}`, duplicate/archive/preview.
Не хватает: визуального WYSIWYG (сейчас только текстовый MJML), каталога готовых шаблонов, вложений к письмам.
Объём: малое доделывание (каталог) / новый модуль (WYSIWYG) / малое доделывание (вложения, schema+логика рассылки уже есть).

## 4. Персонализация писем

**Статус: частично.** `extractVariables` генерична, но `mailer-queue.service.ts:91-97` при реальной отправке прокидывает только `firstName`/`lastName` + служебные `{{landingPageUrl}}`/`{{reportPhishingUrl}}`. Поля `department`/`position`/`customFields` уже есть в модели Employee, но не передаются в рендер.
Объём: **малое доделывание** — расширить объект `data` в mailer-queue.service.ts.

## 5. Индивидуальные ссылки на получателя

**Статус: готово**, эквивалент GoPhish `rid`. `CampaignTarget.trackingToken` (UUID, unique), используется во всех публичных ссылках. Паритет достигнут, доделок не требуется.

## 6. Pixel отслеживания открытия

**Статус: готово.** `GET /t/pixel.gif?token=`, `@Public()`, `no-store`, пишет `email_opened`. Полный эквивалент GoPhish.
Минус: пиксель жёстко вставляется перед `</body>`, нет гибкого `{{.Tracker}}`-плейсхолдера — малое доделывание при необходимости.

## 7. Регистрация переходов по ссылкам

**Статус: готово.** `POST /t/event {type: link_clicked}` из JS-инжекта + `bot-detection.ts` (эвристика по UA — лучше голого GoPhish).
Ограничение: зависит от JS на странице получателя (GoPhish делает это на уровне URL-редиректа). Опционально: редиректный trampoline-эндпоинт без зависимости от JS.

## 8. Регистрация отправки форм

**Статус: готово**, с продуманной архитектурой безопасности. Безопасный путь по умолчанию (`safe-form-injector.ts`, только факт отправки) + отдельный opt-in `/t/credential` с дедупликацией по SHA-256 и ADMIN-only reveal с обязательным AuditLog. Строго лучше и GoPhish, и StopPhish (который писал пароли в открытый лог).

## 9. Управление SMTP

**Статус: частично.** Полный CRUD с шифрованием пароля, `test()` с реальной отправкой, несколько подключений, `isDefault`, умный выбор TLS/STARTTLS по порту.
Не хватает: retry при сбое отправки (явный shortcut в коде — pg-boss это поддерживает, просто не настроено), per-SMTP rate-limit (сейчас только per-campaign), multi-SMTP failover/round-robin, provider-aware throttling (Gmail/Outlook).
Объём: малое доделывание (retry) / новый модуль (failover).

## 10. Управление кампаниями

**Статус: частично.** Backend — полный конечный автомат (`campaign-state-machine.ts`), 4 способа таргетинга одновременно (ручной/группа/сегмент прошлой кампании/случайная выборка), полный набор переходов в контроллере.
Не хватает: повторный запуск по периодичности, отложенный старт реализован но не проверен сквозным прогоном, фронтенд вероятно без многошагового wizard (не читан построчно — предположение по количеству файлов).
Объём: малое доделывание (периодичность) / проверка (отложенный старт) / новый модуль (wizard, если нужен).

## 11. Статистика по сотрудникам

**Статус: готово**, глубина выше GoPhish. `reports.service.ts: employeeDetail()` — полная история по каждой кампании, все типы событий с IP/UA, уникальные варианты credential по хешу. Доделок не требуется.

## 12. Аналитика и отчёты

**Статус: частично.** Только CSV-экспорт (ручная сборка, без библиотеки), два вида (журнал событий, сводка по получателям).
Не хватает: XLSX (подтверждено — зависимости в package.json нет, агрегация данных уже готова), PDF-отчёты (MS AST формирует готовые PDF), экспорт общего дашборда/timeline/compare-campaigns.
Объём: малое доделывание (XLSX) / новый модуль (PDF).

## 13. Импорт и массовое управление сотрудниками

**Статус: частично.** Импорт качественный: построчная валидация, upsert по email, не прерывается на ошибке строки, лимит 20000 (shortcut), история изменений.
Массовое управление: только `bulkAssignGroup`. Нет bulk-delete/deactivate, bulk-update произвольных полей, экспорта сотрудников в CSV, customFields в CSV-импорте.
Объём: малое доделывание на все пункты — паттерн `bulkAssignGroup` уже есть, копировать.

## 14. Управление результатами кампаний

**Статус: частично.** `admin/maintenance` — очистка по возрасту для `audit_logs`/`campaign_events` с предпросмотром количества. Это не retention-политика, а ручная операция.
Не хватает: архивирование кампании как сущности (soft-delete, паттерн `isArchived` уже есть у Template/LandingPage, просто не у Campaign), explicit purge CapturedCredential по дате/кампании (отдельно от каскадного удаления), массовое архивирование.
Объём: малое доделывание на оба пункта.

## Паритет с модулями StopPhish (архитектура донора)

| Модуль StopPhish | Аналог сейчас | Статус |
|---|---|---|
| `license` | нет | Не нужен — другая коммерческая модель (self-hosted open-source) |
| `app.config`/`settings` | `Setting` + `admin/config-registry` | Есть, другая реализация |
| `certificates.tls` | нет модуля, TLS через Caddy вручную | **Отсутствует — ключевая точка роста для модуля "Домены"** |
| `kubernetes.ingress` | нет | Архитектурно неприменимо (Compose, не k8s) — для доменов решать через конфиг Caddy, не копировать идею |
| `auth.saml` | `openid-client` подключён, UI-поток не реализован | Задел есть только в зависимостях |
| `api-hosting` | модуль `pages` целиком | Есть, встроено в монолит |
| `api-website-scraper` | `screenshot.service.ts: clone()` + `pages.service.ts: clonePreview()` | Есть — прямой аналог (граббер) |
| `api-campaigns`/`api-mailer` | `campaigns` + `mailer` в одном монолите | Есть функционально, модульный монолит вместо микросервисов — осознанное решение |
| `dataPackageManager`/`packageManager`/`template` | `templates` модуль | Частичный аналог, нет "пакетного" слоя |
| отдельный `mailserver`-под (+Roundcube) | нет, только исходящий SMTP | Отсутствует осознанно — нет приёма ответов от "жертвы" |

**Вывод для модуля "Домены" (следующий блок работы):** `certificates.tls` и `kubernetes.ingress` — две крупнейшие архитектурные дыры под multi-domain. Реалистичный путь — Caddy on-demand TLS с динамической конфигурацией вместо собственного ACME-клиента и вместо копирования k8s Ingress API.

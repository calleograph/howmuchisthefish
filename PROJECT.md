# PROJECT.md — HowMuchIsTheFish

Текущее состояние проекта. Обновляется после каждого законченного изменения. Журнал изменений — в [HISTORY.md](HISTORY.md).

## Назначение

Платформа для контролируемых учебных фишинговых рассылок (security awareness training). Организация рассылает сотрудникам имитации фишинговых писем, отслеживает открытия/переходы/отправки форм, при необходимости фиксирует факт реальной компрометации (ввод пароля), формирует отчётность для руководителя. Публичный open-source проект (github.com/calleograph/howmuchisthefish), развёртывается самостоятельно через Docker Compose на собственном сервере заказчика.

Преемник внутреннего проекта StopPhish (старая архитектура на доноре 192.168.1.47 — только для чтения/вдохновения, код и данные не копируются).

## Архитектура

Модульный монолит, не микросервисы (см. docs/ARCHITECTURE.md).

- **backend** — NestJS 11, Prisma ORM 6 поверх PostgreSQL 16, pg-boss поверх того же Postgres как job queue (без Redis)
- **frontend** — React 19 + TypeScript + Vite 8 + Tailwind CSS 4 + shadcn/ui (на базе `@base-ui/react`), react-router-dom 7, @tanstack/react-query 5
- **screenshot-service** — опциональный отдельный Node-сервис с Playwright/Chromium для превью страниц и граббера (клонирование стороннего URL в учебную страницу). Не входит в обязательную установку: `docker compose --profile screenshots up -d`
- **root-helper** — systemd-служба на хосте для безопасного самообновления. Backend-контейнер не имеет доступа к Docker socket, общение идёт через файловый обмен (bind mount `/var/lib/howmuchisthefish/updater`, не Docker volume): backend пишет `request.json`, root-служба на хосте читает, выполняет git checkout/build/migrate/restart, пишет статус обратно

## Важные настройки и зависимости

- Все секреты читаются из `.env` в `deployment/`; `compose.yml` не стартует без `DB_PASSWORD`/`JWT_SECRET`/`APP_MASTER_KEY`/`PUBLIC_BASE_URL` (обязательные через `:?` в compose-синтаксисе).
- `CREDENTIAL_ENCRYPTION_KEY` — отдельный опциональный ключ для захвата значений форм, намеренно НЕ выводится из `APP_MASTER_KEY` и не хранится рядом по конвенции (защита "компромисс": отдельный ключ + аудит-лог, не полный E2E — см. docs/SECURITY.md).
- Два способа публикации: встроенный HTTPS через Caddy (`compose.yml`+`compose.caddy.yml`, по умолчанию) или за внешним reverse-proxy (`compose.yml`+`compose.external-proxy.yml`, backend/frontend слушают только 127.0.0.1).
- На тестовом стенде (192.168.1.107) используется локальный `compose.demo-lan.yml` (не коммитится) — публикует 8080/3000 на все интерфейсы для доступа из LAN; при любом `docker compose up -d` на стенде оба файла (`-f compose.yml -f compose.demo-lan.yml`) обязательны, иначе порт наружу пропадает.
- `cpu_shares: 1024` на backend — приоритет живым запросам над фоновой рассылкой.
- CI: `.github/workflows/ci.yml` (lint, typecheck, jest-тесты, build, guard-тест config-registry против schema.prisma, отдельная проверка миграций на реальном Postgres), `clean-os.yml`, `release.yml`. `scripts/ci/private_data_scan.sh` — сканирование на приватные данные перед публикацией.

## Реализованные функции (актуально на v0.3.0)

- Полный жизненный цикл кампании, SMTP-подключения, MJML-шаблоны с персонализацией
- Безопасное отслеживание форм по умолчанию (значения не сохраняются), опциональный захват значений (opt-in за страницу) с отдельным шифрованием и журналируемой расшифровкой
- Граббер страниц — клонирование произвольного URL в учебную страницу через headless-рендер (работает для SPA/JS-форм), автопереписывание form action/method
- Группы с вложенностью, таргетинг по сегменту прошлой кампании и случайной выборкой, настраиваемые поля сотрудников
- Детальная история сотрудника (`/reports/employees/:id/detail`), метрика "скомпрометировано" на дашборде (уникальные сотрудники, не попытки)
- Экран обновления системы из UI с root-helper, защита от отката на более старую версию (двойная проверка — frontend и root-helper)
- Установка одной командой (`install.sh`), резервное копирование/восстановление с шифрованием (CLI)
- Домены: добавление, верификация владения через TXT-запись, привязка к учебной странице, автоматический TLS через Caddy on-demand (`ask`-эндпоинт) при Caddy-деплое, честное предупреждение в UI, если TLS нужно настраивать вручную (external-proxy деплой)

## Известные ограничения (см. docs/FEATURE_MATRIX.md, детали — docs/FUNCTIONAL_GAP_MATRIX.md)

- Домены: сертификаты выпускаются автоматически только при Caddy-деплое; маршрутизация `/lp/*` по кастомному домену работает (Caddy `:443` блок + `on_demand`), но сами кастомные домены пока не обслуживают ничего, кроме `/lp/*`/`/t/*` — это осознанно (кастомный домен не должен отдавать SPA администратора)
- Массовые операции с сотрудниками (кроме назначения в группу) не реализованы ни в UI, ни в API — bulk-delete/deactivate/update отсутствуют
- Персонализация писем передаёт в рендер только firstName/lastName — department/position/customFields сотрудника уже есть в модели, но не прокинуты в mailer-queue.service.ts
- SMTP: нет retry при сбое отправки (явный shortcut в коде), нет multi-SMTP failover, rate-limit только per-campaign, не per-provider
- Отчёты: только CSV (ручная сборка), нет XLSX/PDF
- Визуальных drag-n-drop редакторов (писем, страниц) нет — только текстовый MJML/HTML
- Каталогов готовых шаблонов писем/страниц нет
- Повторный запуск кампании по периодичности не реализован (кампания запускается один раз); планирование отложенного старта реализовано, но не проверено сквозным прогоном
- Резервное копирование доступно только из CLI, кнопки в UI нет
- OIDC/SAML: зависимости подключены, UI-поток входа НЕ реализован
- Журналирование действий администраторов: модель AuditLog есть, активно не используется большинством модулей
- Retention-политика (автоудаление старых событий/журнала) не реализована — только ручная очистка; архивирования кампании как сущности нет (soft-delete есть у Template/LandingPage, но не у Campaign)
- MFA: поля в схеме БД зарезервированы, логика не реализована
- Обновление через UI проверено компиляцией, живой end-to-end прогон с реальной сменой версии не выполнялся
- Caddy-путь публикации проверен только `docker compose config` + реальным `caddy validate`/`caddy adapt` конфигурации (синтаксис подтверждён), но живой выпуск сертификата Let's Encrypt для кастомного домена ещё не проверялся на реальном домене с публичным DNS
